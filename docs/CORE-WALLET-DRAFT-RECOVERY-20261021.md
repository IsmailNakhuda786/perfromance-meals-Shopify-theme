# Durable Core Wallet draft recovery — 21 October 2026

Internal, default-off development storage for the existing provider-neutral Wallet state machine. This is not a payment gateway, credit-lot reservation, native settlement or a second spendable balance. There is no customer route, payment callback or automatic worker. Production preflight rejects activation of `CORE_WALLET_DRAFTS_ENABLED`.

The saved draft binds shop/customer/SGD, attempt, canonical cart and ledger revision, funding allocation, earliest credit expiry, state and revision. Creation is idempotent under competing inserts and refuses a changed plan for the same attempt. Transitions compare the stored revision and entire previous payload atomically. Unknown submitted outcomes remain held; timers cannot release them. A repeated original preparation cannot reopen a finished attempt. A repeated identical provider-fixture receipt returns the same saved draft, without creating a ledger entry or reserve.

Reload validation rejects corrupt JSON, mismatched stored columns, missing submission/terminal evidence, altered allocation binding and inconsistent timestamps. The customer privacy inventory explicitly includes this model. No personal contact details or credentials are introduced by this storage.

Verification: 395 total SQLite Core tests, TypeScript, lint and production schema mirror pass. Twenty-eight focused PostgreSQL tests cover draft recovery/state/privacy with random fixture shops and cleanup. A disposable PostgreSQL schema also reconstructed the full 23-migration provider schema successfully and was removed. SQLite rebuilds all25migrations with zero schema drift (its earlier bootstrap history differs from PostgreSQL). Only the new additive table was then applied in Performance Meals Development; before/after hashes of16existing financial/customer/programme models are identical, and the new table has0rows. No production database was accessed.

The development preview was refreshed with draft persistence and general bundle reviews explicitly off. Existing customer money and historical ledger records remain unchanged. A future supported authenticated payment adapter still needs actual transactional credit-lot locks, final checkout evidence, native settlement and recovery acceptance before any activation. Saving a SUBMITTING or SETTLED fixture state alone does not submit or settle money.

## Currency and market

Required base currency: SGD. Required primary market: Singapore. Actual QA store at audit: PKR; active market list contains Pakistan and Canada, no Singapore. Product, bundle, subscription, programme, cart and checkout correctly use native/current Shopify currency, which is PKR. This does not pass SGD acceptance. Liquid uses money/money_with_currency. Builder receives cart.currency.iso_code (fallback shop.currency) and uses Intl.NumberFormat; no hard-coded currency symbol or exchange calculation.

Store-owner action: configure Singapore/SGD, review numerical QA prices as test prices, replace/confirm shipping and tax settings, gift denominations and selling-plan configuration, then perform targeted SGD QA. Do not merely relabel PKR values in the theme. Shopify documents that changing currency preserves numerical product amounts, leaves shipping rates unchanged and invalidates existing gift-card balances. Existing PKR test orders must remain historical PKR records. Do not delete them or silently rewrite them. Currency change is not performed in this phase.

Reference: https://help.shopify.com/en/manual/payments/shopify-payments/store-currency/changing-your-store-currency

## Business-stream separation: current result is incomplete

Native variants/product references reliably identify the current test line items. Meal Plan order #1002 retains Programme/Meal plan and four date/window selections, plus a private _pm_menu_selection JSON property containing 24 selections. Ready Series subscription order #1001 retains its actual selling plan. However, performance.business_stream does not exist on either product, Ready Series lines have no stream snapshot, and the cart permits products from both streams. This fails the requirement for durable, enforceable separation. No mixed-stream test order was submitted. Metafield content and line properties alone cannot enforce checkout or control fulfillment.

Production-safe recommendation, not implemented here:

1. Define merchant-owned PRODUCT performance.business_stream as required single_line_text_field with allowed values ready_series and meal_plan; distinguish gift cards explicitly under a documented cross-stream policy. Model product purchase kind separately (single/bundle/subscription/programme). Do not infer business stream from translated titles, collection membership, QA handles or customer identity.
2. Theme adds a private _pm_business_stream snapshot to every cart path (product, catalog, builder, gift if relevant), alongside _pm_schema_version and stable external/business keys. Server validation reads authoritative product metafields and rejects missing or forged client snapshots. Theme can explain a stream switch without silently discarding a cart.
3. REQUIRES CUSTOM APP — NEXT PHASE: install a Cart/Checkout Validation Function to reject mixed ready_series/meal_plan transactions across theme, direct cart URLs and accelerated checkout, subject to store/Function eligibility. Specify gift-card mixing policy with Jerome first. App-owned data must preserve original stream and programme identifiers on subscription contracts, orders and fulfillment schedules. Read the trusted stream from products at creation and store an immutable validated snapshot, because products/metafields can change later.
4. REQUIRES CUSTOM APP — NEXT PHASE: idempotent order/subscription webhooks persist validated stream on order/contract metadata and structured operational records; use order metafields as canonical machine data. Optional tags are search conveniences, not the source of truth. Quarantine unknown/mixed legacy records instead of guessing.
5. Customer identity stays shared. Customer account extensions route menu/subscription controls to the correct stream; production/kitchen/billing/reporting partitions use stream-qualified records and reference mappings. Admin extensions/App Home are later implementation surfaces, not an external Admin platform.

## fresher.com.sg migration safety

No migration performed. Maintain an explicit mapping of legacy customer IDs/emails (identity resolution with consent/security review), product/variant/SKU IDs, programme keys, bundle components, menu/week/window identifiers, orders, contracts and gift/rewards balances to destination Shopify IDs. Namespace mappings by source system plus business_stream and preserve provenance/version. Handles are portable lookup inputs but can change; do not use them as immutable external identity. Resolve destination references at setup/import time rather than embedding dev IDs in code. Customer passwords and payment tokens require provider-supported migration/reauthorization; do not assume exportability or manufacture tokens. Subscription contracts require owning app/payment compatibility and a tested migration path. Reconcile duplicate customers, balances, future commitments and cutoffs before activation. QA records/prices/customers are distinguishable test records and must never seed production assumptions.
